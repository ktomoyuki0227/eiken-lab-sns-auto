## 1. プロジェクト概要

| 項目 | 内容 |
|------|------|
| 案件名 | 英検ラボ SNS 自動投稿システム |
| クライアント | 長畑さん（Groovy House 経由） |
| 開発担当 | 久保友幸（1人で進める） |
| 対象事業 | Nippon English School（NES）> 英検ラボ |
| 目的 | SNS への定期投稿を自動化する（V1：note を最優先で着手、Instagram は後続フェーズで展開、最終的には全SNS対象） |
| 開発期限 | 2026年4月末（V1完成目標） |
| 開発プラットフォーム | Dify（ノーコード LLM ワークフロー） |

### Dify を選んだ理由

以下のツール比較をもとに、今回の要件に最も合致する Dify を採用した。

| ツール | 強み | 弱み | 今回の適合度 |
|--------|------|------|------------|
| Dify | ノーコード LLM ワークフロー専用。Knowledge（RAG）・スケジューラ・HTTP ノードが一体。LLM プロンプト管理が直感的。 | エンジニア以外には学習コストが少しある。 | ◎ 最適 |
| n8n | 汎用自動化ツール。豊富なインテグレーション。セルフホストで無料。 | LLM 専用機能が薄い。プロンプト管理・Knowledge が別途必要。 | △ LLM 用途には遠回り |
| Zapier / Make | ノーコード自動化。セットアップが簡単。 | 無料枠が非常に狭い。LLM ノードは別途連携が必要で複雑。有料プランは高額。 | △ コスト面で不利 |
| LangChain / LangFlow | LLM パイプラインに特化。柔軟性が高い。 | コード知識が必要。非エンジニアには難しい。運用保守コストが高い。 | △ 開発コストが高い |
| フルスクラッチ（Node.js 等） | 自由度が最大。ロジックを完全にコントロールできる。 | 開発・保守コストが最大。今回の納期・規模に不釣り合い。 | ✕ オーバースペック |

採用決定の根拠：
1. LLM プロンプト管理・Knowledge・スケジューラがノーコードで完結する
2. 長畑さん自身が Dify ワークスペースを確認・操作できる（透明性が高い）
3. 開発初期は友幸の Gemini 無料枠、最終検証は長畑さんの Claude クレジット3000円で低コスト運用が可能
4. 将来的に他コースへ横展開する際もワークフローを複製するだけで対応できる

## 3. 要件定義

### 3-1. 機能要件

| # | 機能 | 概要 |
|---|------|------|
| F1 | 情報収集 | 毎日定時に英検関連ニュース・時事ネタを自動収集 |

## 3.5 コンテンツ方針（2026-05-04 中村さんとのミーティングで確定）

### AI感をなくす方針

AIが書いた文章に見えることでユーザーが離れるリスクがある。特にnoteはこの対策が最優先。

対応方針：
- noteの冒頭に「エピソード・失敗談・転機・気づき」を一人称で100字程度入れる
- 箇条書きを減らし、話し言葉ベースの文体にする
- 体験談は一人称（「私は〜」「あるとき〜」）で書く
- 構成変更：タイトル → 冒頭エピソード → 問題提起 → 解決策 → まとめ

実装：各ワークフローのLLMプロンプト（noteセクション）を上記方針で改修する（workflow-build.md参照）。

---

### X投稿の方針

自動生成で作るX投稿の構成：

| 優先度 | 内容 |
|-------|------|
| 必須 | 同日生成のnoteと同じ内容の短縮版 |
| 必須 | noteへの誘導CTA |
| 任意 | 英語のtips・スクール紹介・近況報告など |

引用リツイートへの対応は自動化が困難なため中村さんが手動で対応する。自動生成の対象外。

---

### 分析→コンテンツへの反映方針（V2）

Google Sheetsで投稿記録を蓄積し、バズった投稿の要素を再現性のある形でコンテンツ生成に活かす。

ステップ：
1. 投稿ごとにGoogle Sheetsに記録（自動生成分・外注分の両方）
2. 反応が良かった投稿に「バズ要因」を手動でメモ（中村さん担当）
3. バズ要因をDBに保管し、LLMへの参考情報として渡す
4. 再現性の高い投稿パターンを蓄積していく

※ 2週間以内のコンテンツ重複防止（直近14件参照）は前提として維持する。

## 4. 投稿仕様

### 4-1. 対象SNSと展開フェーズ

最終的には以下の全SNSへの自動投稿を目指す。各SNSに最適化したフォーマットで生成する。

| SNS | フェーズ | 状況 |
|-----|---------|------|
| note | V1（最優先） | テキストベースで現実的。まず note から着手する |
| Instagram | V1後半〜V2 | note の動作・品質確認後に展開。リール台本形式 |
| X（Twitter） | V3以降 | 短文・拡散特化のフォーマットで対応予定 |
| LINE | V3以降 | LINE公式アカウント向け配信文を想定 |
| ブログ | V3以降 | SEO特化の長文記事形式で対応予定 |

### 4-2. 制作量・運用フロー（V1）

V1 では note を最優先で着手する。Instagram は note の動作・品質確認後に展開する。

| SNS | 生成本数 | 投稿本数 | 確認者 | 保存先 | V1 優先度 |
|-----|---------|---------|-------|-------|---------|
| note | 3候補/回 | 1本/回 | 長畑さん | Google Drive（Google ドキュメント） | 最優先 |
| Instagram | 3候補/回 | 1本/回 | 長畑さん | Google Drive（Google ドキュメント） | V1後半〜V2 |

保存ファイル名（1回の実行で2ファイル生成）：
- `YYYY-MM-DD note`：note 候補3本
- `YYYY-MM-DD Instagram`：Instagram 候補3本

運用フロー：
1. Dify が自動起動（生成時刻は下記参照）
2. note 用3候補 + Instagram 用3候補を生成
3. 長畑さん提供の Google Drive フォルダ内に2ファイルを並列生成して保存
4. 長畑さんがフォルダ内のドキュメントを確認し、各SNSで1本ずつ選んで投稿

生成時刻：毎朝8:00 JST（Dify スケジュールトリガー設定値・変更可能）

更新頻度の考え方：毎日生成すると6候補/日ペースで溜まるため、コンテンツの重複・負荷を防ぐ観点から週1回（週3候補）での運用も検討中。実際の投稿ペースと長畑さんの確認工数に応じて最適な頻度を設定する（詳細は Section 11 参照）。

### 4-3. ターゲット

英検合格を目指す中高生。英検勉強中だが継続できていない・やり方がわからない・何から始めればいいか迷っている層を主なターゲットとする。

note については、子どもの英検合格を支援したい親御さん向けのコンテンツも一定割合で生成する（子どもへの英語教育への投資を検討している保護者層）。

### 4-4. CTA（Call to Action）

CTA（シーティーエー）とは「Call to Action（行動喚起）」の略で、コンテンツを見た人に「次にしてほしい行動」を促す一言のことです。動画や記事の最後に入れることで、「見て終わり」にならず、体験申し込みや問い合わせなどの具体的なアクションにつなげる役割を持ちます。

全コンテンツ共通で以下を使用する。

```
無料体験レッスンまたはお問い合わせはこちら
→ https://eikenlab.jp
```

### 4-5. コンテンツカテゴリ（ローテーション）

3候補を生成する際は異なるカテゴリを混ぜ、多様性を持たせる。
媒体によって各カテゴリの使用割合を変化させる（例：Instagram は行動喚起系・悩み系を多め、note は試験対策系・親御さん系を多め）。

| カテゴリ | 訴求内容 |
|---------|---------|
| 悩み系 | 現状に共感→自分ごと化 |
| 習慣化系 | 継続できない原因の言語化→納得感 |
| 効率系 | 非効率な勉強法への不安→正しい方法への関心 |
| 試験対策系 | 英検特有のコツ・対策情報 |
| 行動喚起系 | 迷いを断ち切る→即行動 |
| 時事系 | 英検関連ニュース・試験日程と連動したネタ |
| モチベーション系 | 合格後の未来・理想像を想起させる |
| 親御さん系 | 子どもへの英語教育投資を後押しする内容（note 向け） |

#### カテゴリを増やしたい場合

操作手順：Dify のワークフロー内にある LLM ノードのプロンプトを編集し、カテゴリ一覧の箇所に1行追加するだけで対応できる。

運用フロー（長畑さんからリクエストがある場合）：
- リクエストはすぐに対応できないため、定期レビュー（月1回程度を想定）の形で意見を集める
- 把握でき次第、友幸（現時点は1人で担当。将来的に南村くんがジョインする可能性あり）が Dify のプロンプトを更新する
- 緊急性が高い場合は個別に相談

### 4-6. Instagram コンテンツフォーマット

※ 以下のフォーマットはまだ実績データがないため仮定義。実際に投稿を開始して反応を見ながら V2 以降で随時アップデートする。

プラットフォーム特性：縦型ショート動画（リール）。視覚・聴覚で瞬時に刺さる短いセリフが命。中高生に刺さる話し言葉・テンポ感を意識する。

出力する項目：

```
【タイトル】
動画のフックとなる一言（画面テキストに重ねる想定）

【台本】
各セクションを時間軸で区切る。セリフは短く・話し言葉で。

0〜3秒（Hook）：
  共感・衝撃・問いかけの一言
  例）「英検、また落ちた…」

4〜11秒（Agitate）：
  問題を深掘り。不安・共感をさらに喚起
  例）「やる気はあるのに、やり方がわからない」
  例）「なんとなく単語だけやっても、本番で点が取れない」

12〜18秒（Solution）：
  解決の方向性をチラ見せ。具体的すぎず、続きを見たくなるように
  例）「合格する人には、共通する勉強の順番がある」

最後2秒（CTA）：
  「無料体験レッスンまたはお問い合わせはこちら」

【キャプション（投稿本文）】
1〜2行のフックテキスト（本文冒頭に表示される部分）
空行
ハッシュタグ（10〜15個）
  英検関連：#英検 #英検対策 #英検勉強法 など
  ターゲット関連：#中学生 #高校生 #英語勉強 など
  拡散狙い：#英語学習 #受験英語 など
```

総尺の目安：15〜25秒

### 4-7. note コンテンツフォーマット

プラットフォーム特性：テキストブログ。検索経由で読まれることが多く、SEOと読みやすさが重要。中高生が「参考になった」と感じて最後まで読める情報量と構成を意識する。Instagram と違い、読者に実際の価値（知識・気づき）を提供することが目的。

ターゲット構成：中高生向けと親御さん向けを混在させる。目安は週3〜4本が中高生向け、週1〜2本が親御さん向け（子どもへの英語教育投資・英検の有効性を伝える内容）。

出力する項目：

```
【タイトル】
検索意識・悩み解決型のタイトル
  例）「英検3級に3回落ちた私が、4回目で合格できた理由」
  例）「英検のリスニングが聞き取れない人へ【これだけ変えた】」
  例）「英検2級を目指す高校生が、最初にやるべきたった1つのこと」

【リード文（100〜150字）】
読者の悩みに共感し、記事の価値を伝える導入文。
  例）「英検の勉強を始めたのに、全然点が伸びない…と悩んでいませんか？
  　　実は多くの人が、最初に間違った順番で勉強しています。
  　　今回は、合格者が共通してやっている勉強の流れを紹介します。」

【本文（800〜1200字）】
セクション見出しを使って読みやすく構成する。
  - 問題の深掘り（なぜ伸びないのか）
  - 具体的なアドバイス or 知識（英検に特化した内容）
  - 実践イメージ（中高生でも今日からできること）

【まとめ（3〜5行）】
記事の要点を箇条書きで整理。読み飛ばした人にも伝わるように。

【CTA】
「英検合格をサポートする無料体験レッスンを実施中です。
まずはお気軽にご相談ください。
→ https://eikenlab.jp」
```

## 5. システム構成

### 5-1. 全体アーキテクチャ

```
【日次：コンテンツ生成ワークフロー（毎朝8:00 JST）】※ V1から実装

Dify スケジュールトリガー
    ↓
Code ノード 1（JST 日付生成）
    ↓
【V1】LLM ノード（Gemini 2.5 Flash Lite → 最終検証時に Claude Haiku へ切り替え）
  ：LLM 自身の知識をもとに Instagram 1候補 + note 1候補を JSON 生成
  ※ V1 はリアルタイム Web 検索なし（詳細は Section 8 参照）
  ※ V2 以降：Tavily Search で最新情報を収集してから LLM に渡す構成に変更予定
    ↓
Code ノード 2（JSON パース → ドキュメント本文テキスト整形）
    ↓（並列）
HTTP ノード × 2（GAS 経由で Google Drive にドキュメントを作成・書き込み）
  - 「YYYY-MM-DD Instagram」
  - 「YYYY-MM-DD note」
    ↓
【V2から】Knowledge 参照ノード：過去分析から「伸びるコンテンツの傾向」を取得
    ↓
長畑さんがフォルダ内のドキュメントを確認 → Instagram 1本・note 1本を選んで投稿

─────────────────────────────────────────────

【週次：分析・ナレッジ更新ワークフロー（週1回）】※ V2から実装

Dify スケジュールトリガー
    ↓
HTTP ノード：Instagram Graph API から分析データを取得
    （インプレッション・リーチ・継続視聴数など）
    ↓
LLM ノード（Claude Haiku）：「今週の傾向まとめ」を文章化
    ↓
Dify Knowledge に保存
    （次回の日次ワークフローで自動参照される）

─────────────────────────────────────────────

【常時：PDCAダッシュボード（V2以降）】

Google スプレッドシート（分析データ蓄積）
    ↓
Google Looker Studio で可視化（無料）
```

## 8. 情報収集ソース

### このシステムが目指す最終形

毎日、英検に関する最新ニュース・試験情報・トレンドをリアルタイムで自動収集し、その情報を素材にしてコンテンツを生成する。これが本システムの根幹であり、ゆずれないゴールです。

### V1 での情報収集について（長畑さんへの説明）

**当初の計画と、変更に至った経緯をご説明します。**

当初、リアルタイム情報収集には **Tavily Search**（AI エージェント向け Web 検索 API）を採用する予定でした。しかし、Dify ワークスペースの権限設定の関係で、V1 では導入が難しいことが判明しました（Tavily の API キー登録には Dify の Admin 権限が必要で、現時点では長畑さんに Admin 権限の設定をお願いする準備が整っていません）。

次に、Dify の標準的な Web Search 機能を代替として検討しました。しかし、Dify の現バージョンではすべての Web 検索ツールに外部 API キーが必要であり、かつ無料で安定して使えるサービスが現時点ではなくなっていることが判明しました（参考：Brave Search は2026年2月に無料枠を廃止）。

そのため **V1 ではリアルタイム情報収集を一旦除外し、LLM（AI）自身が持つ英検に関する豊富な知識をもとにコンテンツを生成する**方式で進めます。これは一時的な簡易版であり、最終ゴールは変わりません。

### フェーズ別の収集方針

| フェーズ | 収集方法 | 備考 |
|---------|---------|------|
| V1（現在） | なし（LLM の学習データを使用） | リアルタイム情報なし。英検の一般知識・勉強法・試験対策が中心 |
| V2 以降 | Tavily Search | 長畑さん（Admin）が Dify に API キーを登録。毎日の最新情報を自動収集 |

### V1 での時事系コンテンツの扱い

カテゴリの一つである「時事系」（英検関連ニュース・試験日程と連動したネタ）は、V1 では LLM が生成日の日付をもとに推測できる範囲（試験シーズン・年度切り替えなど）で対応します。最新ニュースとの連動は V2 以降で実現します。

### V2 以降：Tavily Search への切り替え手順

V1 の動作確認後、以下のステップで Tavily を導入する。

1. 長畑さん（Admin）が Tavily アカウントを作成・API キーを発行
2. 長畑さんが Dify のワークスペース設定から Tavily の API キーを登録
3. ワークフローに Web Search ノード（Tavily）× 3 本と Variable Aggregator を追加
4. LLM ノードのユーザープロンプトに検索結果を渡す形に更新

### V2 での検索クエリ候補

- 「英検 ニュース」＋今日の日付
- 「英検 試験日 申し込み」
- 「英検 勉強法 おすすめ」
- 「英語学習 トレンド」
